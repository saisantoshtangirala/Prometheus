# Forensic audit — Kronos / Prometheus / NightEvolver / CHIMERA

**Date:** 2026-08-20 · **Commit:** `acd0692` · **Scope:** 20,193 LOC across
`kronos/` (5,641), `prometheus/` (7,059), `nightevolver/` (4,632),
`chimera/` (2,921), `scripts/` (2,445), plus 10,628 LOC of tests.

**Verdict on the audit question — "does this system do what it claims,
reliably and without hidden failure modes?"**

> **No.** The headline claim — *RunPod trains nightly, Hetzner executes
> the result* — is **false for the NightEvolver path**. RunPod trains a
> GA, writes a checkpoint, ships it to Hetzner, and **nothing on Hetzner
> ever reads it.** `kronos/` contains zero references to `nightevolver`.
> The training half runs; the execution half was never wired.

Everything else in this report is secondary to that.

## 1. Comprehensive bug report

### CRITICAL

---

**C1 — The NightEvolver checkpoint is delivered and then ignored.**

- **File:** `kronos/orchestrator.py:671-700`, `.github/workflows/train-runpod.yml:340-395`
- **Severity:** **Critical**
- **Description:** `train-runpod.yml` mode `nightevolver-ga` runs the GA,
  writes `checkpoints/nightevolver/nightevolver_best.json`, tars
  `checkpoints/`, and scps it to Hetzner. The orchestrator's
  `load_checkpoint()` calls `load_runpod_checkpoint(self.reflex.snn, ...)`,
  which loads **`checkpoints/runpod/meta/snn.pt`** — a torch SNN
  state dict. Nothing reads the GA's JSON.
- **Evidence:**
  - `grep -n "nightevolver" kronos/*.py` → **zero matches.**
  - `nightevolver/saver.load_checkpoint` and
    `nightevolver/strategy_decoder.EvolvedStrategy.from_checkpoint` are
    called only from `scripts/` and `tests/`, never from `kronos/`.
  - Compounding it, the delivery step untars with
    `--strip-components=1` into `checkpoints/runpod/`, so the file lands
    at `checkpoints/runpod/nightevolver/nightevolver_best.json` — a
    different path from the `checkpoints/nightevolver/` that
    `saver.load_checkpoint()` defaults to. Even a corrected consumer
    would miss it.
- **Impact:** Every `nightevolver-ga` run — including the successful
  RunPod run `32335279505` — is compute spent on an artifact with no
  consumer. The deflated-Sharpe gate that "Hetzner enforces" is never
  reached, because Hetzner never loads the checkpoint to gate it.
- **Recommendation:** Either (a) add a `run_nightevolver()` phase to the
  orchestrator that calls
  `EvolvedStrategy.from_checkpoint(path, require_gate=True)` and routes
  its `signal()` into `paper_trader`, or (b) if the GA path is
  research-only, remove `nightevolver-ga`/`-rl` from the workflow's mode
  choices so it cannot masquerade as a production pipeline. Do not leave
  it in the current state, where a green CI run implies a deployment
  that did not happen.

---

**C2 — GPU pod can leak with no sweeper (cost).**

- **File:** `.github/workflows/train-runpod.yml:244-289` (create), `:397-403` (terminate)
- **Severity:** **Critical** (billing)
- **Description:** Termination is guarded by
  `if: always() && steps.create.outputs.pod_id != ''`. The pod is created
  by the `POST /pods` at line 253 and billing starts immediately, but
  `pod_id` is not written to `$GITHUB_OUTPUT` until line 288 — after a
  loop that may iterate over several GPU candidates. **Any cancellation,
  runner loss, or hard kill inside that window leaves a running GPU pod
  that the terminate step will skip**, because the guard sees an empty
  `pod_id`.
- **Second leak path:** if `POST` succeeds but the response fails
  `jq -r '.id // empty'` (malformed/partial JSON), `ID` is empty, the
  loop logs "no capacity" and **creates another pod** — while the first
  one runs untracked.
- **Evidence:** Read of the step; there is no `trap`, no pre-write of a
  provisional id, and `grep -rn "orphan\|list.*pods"` across
  `.github/`, `kronos/`, `scripts/` returns **no sweeper of any kind**.
  Pods are named `kronos-ci-${{ github.run_id }}`, so they *could* be
  swept by name — nothing does.
- **Recommendation:** Three changes, cheapest first:
  1. Write `pod_id` to `$GITHUB_OUTPUT` **immediately** after the POST
     returns an id, before the `break` and before any further work.
  2. Treat a POST that returns 2xx-but-unparseable as a possible
     creation: abort rather than trying the next candidate.
  3. Add a scheduled sweeper workflow: `GET /v1/pods`, delete anything
     named `kronos-ci-*` older than the job timeout. This is the only
     control that survives a lost runner.

**H1 — NSE holiday calendar expires in ~4 months.**

- **File:** `kronos/calendar_utils.py:108-140`
- **Severity:** **High** (hard deadline: 2027-01-01)
- **Description:** `NSE_HOLIDAYS_BY_YEAR` contains **2026 only**.
- **Evidence:** executed directly —
  ```
  2024 -> 0 holidays   [warning: falling back to weekday-only]
  2025 -> 0 holidays   [warning]
  2026 -> 15 holidays
  2027 -> 0 holidays   [warning]
  2028 -> 0 holidays   [warning]
  ```
  From 2027-01-01 the system treats **every** NSE festival holiday as a
  trading day: the RunPod scheduler will provision pods on holidays
  (cost), and the orchestrator will expect market data that does not
  exist.
- **Mitigating:** it does log a warning rather than failing silently —
  good design, but nobody reads Hetzner logs daily.
- **Recommendation:** Add 2027 and 2028. Better: make the missing-year
  fallback **raise** for the *current* year rather than warn, so the
  failure is loud on 2027-01-01 instead of quietly wrong all year.

---

**H2 — The training SSH has no timeout; a frozen pod bills for 4 hours.**

- **File:** `.github/workflows/train-runpod.yml:334`
- **Severity:** **High** (billing + silent hang)
- **Description:** The sshd-wait probe at line 320 uses
  `-o ConnectTimeout=5`. The actual **Train** invocation at line 334 has
  **no `ConnectTimeout`, no `ServerAliveInterval`, no `ServerAliveCountMax`.**
  If the pod accepts the TCP connection and then freezes (network
  partition, OOM, hung kernel), `ssh` blocks until the job-level
  `timeout-minutes: 240` fires — up to **4 hours of GPU billing on a
  dead pod**.
- **Evidence:** `grep -n "ConnectTimeout\|ServerAlive" train-runpod.yml`
  → only line 320. Note `scripts/ssh_train.sh:57` *does* set
  `ServerAliveInterval=30` — so the hardening exists in the repo and was
  simply not applied to the path CI actually uses (see M3).
- **Recommendation:** Add
  `-o ServerAliveInterval=30 -o ServerAliveCountMax=6 -o ConnectTimeout=15`
  to lines 334 and 368, and a per-step `timeout-minutes` well under the
  job timeout.

**H3 — The backtest holds overnight short positions, which NSE cash does not permit.**

- **File:** `nightevolver/ga_engine.py:255, 267, 292`
- **Severity:** **High** (inflates every backtest result)
- **Description:** `simulate()` opens positions as
  `pos[want] = np.sign(scores[t][want]) * size` — negative sizes
  allowed — and carries them across bars via the `short_a = active & (pos < 0)`
  branch, for up to `hold_days` (now **90**). In the NSE **cash**
  segment under CNC (delivery), short positions **cannot be held
  overnight**; they must be squared off same-day or they go to auction.
- **Evidence:** code read above; `scripts/kite_preflight.py:88` in this
  same repo documents that CNC is the required product and that MIS
  squares off intraday — so the constraint is known elsewhere in the
  codebase and simply not enforced in the simulator.
- **Impact:** roughly half the backtest's opportunity set is
  unimplementable. Every Sharpe, profit factor and win rate reported
  from `simulate()` is optimistic by an unquantified amount.
- **Recommendation:** Add a `long_only: bool = True` parameter to
  `simulate()` defaulting to the tradeable reality, and re-run the
  8-seed comparison. If short signals are wanted, they need a
  futures/MIS execution path that does not currently exist.

### MEDIUM

**M1 — Telegram notifier has no deduplication, rate limiting, or retry.**
`kronos/notifier.py:66-92`. `send()` posts once, returns False on
failure, never retries. There is no cooldown and no suppression of
repeated identical messages. A data-fetch failure in a loop produces one
Telegram message per occurrence — and if Telegram rate-limits (HTTP 429),
the alert is simply lost with a `logger.warning`. The primary human

last-sent/hash cooldown and one retry on 429/5xx.

## 2. Phase-by-phase findings

### Phase 2 — Data integrity & leakage: **substantially PASS**

This is the strongest area of the codebase, and the brief's specific
concern (the NEAT target-leak bug) is **not reintroduced**.

- **Look-ahead:** verified by executable tests, not inspection —
  `test_no_lookahead_in_indicators` (mutate future bars, assert earlier
  rows unchanged), `test_forward_returns_are_correctly_aligned`
  (`forward_returns[t]` is the t→t+1 move), `test_targets_are_strictly_forward_looking`,
  `test_vol_targeting_does_not_look_ahead`,
  `test_flow_features_do_not_see_the_future`,
  `test_no_lookahead_end_to_end` (chimera). All pass.
- **`shift(-1)` alignment:** the brief asks whether the backtest uses
  `shift(-1)`. It does **not**, deliberately — it builds an explicit
  `forward_returns` matrix (`data_loader.py`) and asserts the alignment
  in a test. The only `shift()` calls are `shift(1)` (backward, correct)
  at `data_loader.py:105` and `flows.py:337`.
- **Flow publish-lag:** `flows.align_flow_features` **raises** on
  `lag_bars < 1` rather than warning — correct, since the NSCCL report
  is published after the close it describes.
- **Missing data:** the "drop the date if one symbol is missing" bug is
  fixed *in the bhavcopy path* (`nse_prices.py:249-263`, drops thin
  symbols before dates) — **but the brief's claim that it is universal
  is not verified and appears false**: `data_loader.build_market_data`
  still does `close.dropna(how="any")` unconditionally. Different
  loader, same failure mode. **Medium**, folded into the refactoring list.
- **Genome serialisation across GPU/CPU:** the checkpoint is **JSON, not
  pickle**, and stores plain floats — so there is no device or dtype
  drift possible, and no arbitrary-code-execution risk on load.
  `genome_version` and the full `indicator_names` ordering are verified
  at load. This is done correctly.

### Phase 4 — Training pipeline: **PASS with one caveat**

- **Cost symmetry:** `turnover = |diff(positions)|` (`ga_engine.py:301`)
  — symmetric in long and short by construction. **PASS.**
- **Chronological split:** `kronos/backtest.py:16, 88` — `fit()` sees
  only the train window, `weights_for()` only data ≤ t-1. **PASS.**
- **Validation seed:** the GA seeds population and operators from
  `cfg.seed`; validation is a *disjoint time window*, not a reseed,
  which is the correct control for time series. The brief's question
  ("does validation use a different random seed") assumes an iid
  setting that does not apply here.
- **Caveat:** convergence is healthy but the overfitting gap is
  **+2.42 Sharpe** (IS +2.30 vs OOS −0.12) on the 48-name run. That is
  measured and reported, not hidden.

### Phase 3 — Infrastructure: **FAIL** (C2, H1, H2)

Idempotency is better than the brief assumes: the orchestrator keeps
`_evolution_progress` (`orchestrator.py:132, 289-309`) for
generation-level resume, and `risk_guard` holds halt state in a **file**
(`risk_guard.py:16-20`) precisely so a restart cannot clear it. Those
are good designs. The failures are all at the RunPod seam.

### Phase 5 — Execution: **PASS on structure**

`paper_trader.py` uses a single connection with
`check_same_thread=False` guarded by a `threading.Lock` (`:94-98`), with
`isolation_level="IMMEDIATE"`, and a reconnect-and-retry-once path on
`sqlite3.Error` (`:390-413`). Connections are closed on `close()`
(`:435`). The concurrency question in the brief is handled.
**Not verified:** slippage. There is no slippage model anywhere —
costs are a flat 22bp on turnover. For ₹10,000 notional on liquid
large caps that is defensible; it should be stated rather than implied.

## 3. Missing tests

Ordered by the risk they leave uncovered.

1. **No test that the NightEvolver checkpoint reaches a consumer.** The
   gap in C1 is invisible to the suite because both halves are tested in
   isolation. Needed: an integration test that runs
   `train_nightevolver.py --synthetic`, then asserts the orchestrator
   loads and gates that artifact.
2. **No test for RunPod API failure modes** — timeout, 429, 5xx,
   malformed JSON from `POST /pods`. C2's second leak path would be
   caught by a single test feeding unparseable JSON to the create loop.
3. **No test that a pod is terminated when the training step fails.**
   The `always()` guard is asserted by reading YAML, never executed.
4. **No test for holiday-table expiry.** A test asserting
   `nse_holidays(current_year + 1)` is non-empty would have flagged H1
   months before it bites.
5. **No test that `simulate()` respects a long-only constraint** (H3).
6. **No test for notifier behaviour under repeated errors or HTTP 429**
   (M1).
7. **No test for orchestrator restart mid-Evolution.** `_evolution_progress`
   exists; nothing exercises the resume path.
8. **No test for disk-full or OOM behaviour** on the 8GB/2vCPU box. The
   brief asks about log growth — there is no logrotate config in the
   repo and no watchdog.
9. **No test that `build_market_data`'s `dropna(how="any")` does not
   delete the panel** when one symbol is thin (the non-bhavcopy loader).

## 4. Risk assessment — top 3

**Risk 1: The system reports success for work that was never deployed.**
*(C1)* A green `train-runpod.yml` run currently means "a GA was trained
and a file was copied", not "a strategy is live". Anyone reading CI as a
deployment signal is reading it wrong. This is the most dangerous class
of defect in the repo because it is silent, and because the
deflated-Sharpe gate — the control that prevents trading a bad strategy
— **lives on the consumer side that does not exist.** If a consumer is
added carelessly later, it could easily be added without the gate.

**Risk 2: Unbounded GPU billing with no backstop.** *(C2 + H2)* Two
independent paths leak money: a pod created but untracked (cancellation
race, or unparseable create response), and a pod that hangs for the full
4-hour job timeout because the training SSH has no keepalive. There is
**no orphan sweeper**, so the only backstop is a human noticing the
RunPod console. Worst case is a pod running until manually killed.

**Risk 3: The backtest models trades the venue will not accept.** *(H3)*
Overnight shorts are impossible in NSE cash under CNC, and the simulator
holds them for up to 90 days. Every result produced by `simulate()` —
including the redefinition study and the 48-name run — is measured on an
opportunity set roughly twice the real one. The conclusion those runs
reached (*no edge*) is unlikely to reverse, but any future positive
result would be untrustworthy until this is fixed.

**Honourable mention (not top-3 only because the deadline is known):**
H1's holiday table expires 2027-01-01.

## 7. Single point of failure — stated plainly, as requested

**The Hetzner box is the single point of failure.** It holds the only
copy of `logs/trades.db` (gitignored, so not in version control) and
runs the only execution loop.

It is **partially** protected, and the audit's first draft understated
this — correcting it here rather than leaving the stronger claim
standing. `scripts/hetzner_bootstrap.sh:104-126` installs a systemd unit
with `Restart=always` and `RestartSec=30`, so a crash or OOM-kill *does*
bring the process back. That is real protection against the most likely
failure.

What is genuinely absent:

- **No logrotate.** The unit uses
  `StandardOutput=append:/var/log/kronos-service.log` with no rotation
  configured anywhere in the repo (`grep logrotate` over `scripts/`,
  `deploy/`, `docker/` → zero hits). On an 8GB box that log grows
  without bound, and `Restart=always` will happily restart a process
  into a full disk **forever**, in a tight 30-second loop — which is
  precisely the crash-loop shape this project already hit once with the
  sqlite `audit()` bug.
- **No disk or memory monitoring**, and no `MemoryMax=` on the unit.
- **No alert on restart.** systemd restarting silently means a
  crash-looping service looks identical to a healthy one from the
  outside.
- **No off-box backup of `trades.db`.** The record of every paper trade
  exists on exactly one disk.

So the accurate statement is not "unmonitored" but: **it recovers from
crashes and is blind to the conditions that cause them.** A missing
Telegram report is the only external symptom — and per M1, that is also
what a notifier failure looks like, so the two are indistinguishable to
an operator.
