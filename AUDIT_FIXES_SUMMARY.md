# Audit Fixes Summary

Fixes for the six bugs found in the deep code audit (Priority 1A/1B, 2A/2B/2C, 3B).
Each fix is scoped to the file(s) that actually needed to change to close the bug
without breaking the shape/behavior contracts other code depends on - in two cases
(1A, 2A) that meant deviating from the literally-suggested patch, explained below.

All changes are additive/surgical: no files were rewritten, no new abstractions or
features were introduced, and no CLI/config interfaces changed.

## Priority 1 — Critical

### 1A. NEAT fitness function leaking the target into its own input

**Files:** `kronos/backtest.py`, `kronos/evolver.py`, plus a forced ripple into
`kronos/warmer.py` and `kronos/orchestrator.py` (explained below).

The bug, verified: the fitness target `y` was the last bar of a `horizon`-bar
synthetic future, and `X` was that same future flattened *including that same last
bar*. A genome could score well purely by copying `X`'s last `n_assets` values to
its output - no relationship to market dynamics required.

**Deviation from the suggested patch, and why:** the suggested fix
(`X = future[:-1, :]`) shrinks the model's own input width from `horizon` bars to
`horizon - 1` bars. In `kronos/evolver.py` that's the only option (the
`NightmareBuffer` is exactly `horizon` bars, generated by the diffusion pipeline -
there's no bonus bar to hold out instead), so that's what's implemented there,
**and it forces the same width change onto every other consumer that feeds a
`horizon`-bar window into a `KronosEvolver`-decoded model**: `kronos/warmer.py`'s
`KronosWarmer.support_set()` (production's real nightly MAML warm-up) and
`kronos/orchestrator.py`'s `_master_signals()` (the reporting-only NEAT
inference). Both were updated to build `(horizon - 1)`-bar windows to match, or
they'd have started raising shape-mismatch errors every single night.

In `kronos/backtest.py`, by contrast, `KronosStrategy` owns its own private
bootstrap (`_bootstrap_futures`), so a strictly more contained fix was available
and used instead: bootstrap **one bar longer** (`horizon + 1`), use the first
`horizon` bars as `X` (unchanged width - matching `weights_for()`,
`_calibrate_size_scale()`, and the MAML warm-up tail construction exactly as
before), and use the extra bar as `y`. Zero ripple to any other method in that
class.

**Verified:** `tests/test_audit_fixes.py::TestNoTargetLeakage` (4 tests) - confirms
the target bar is never reachable from `X`'s own trailing slice in either
implementation, and that both `KronosStrategy.fit()` and `KronosEvolver` still
produce working models with the corrected shapes.

### 1B. MAML inner-loop adaptation was a complete no-op

**File:** `prometheus/meta/maml_engine.py`

`_forward_with_params()` called `self.model(X)` (live weights) instead of using
the passed-in adapted parameter clones, so `torch.autograd.grad(loss,
adapted_params, allow_unused=True)` always returned `None` for every parameter,
zero-filled, leaving "adapted" params bit-identical to pre-adaptation on every
step. Fixed using `torch.func.functional_call(self.model, params, (X,))`, which
threads the loss's autograd graph through the passed-in `params` dict instead of
the model's live registered weights.

`kronos/warmer.py`'s `ClippedMAML` inherits this method unchanged, so it's fixed
automatically - no separate change needed there.

**Verified:** manual toy-model + real `WeightedEnsemble` (nested NEAT-decoded
module) smoke tests, plus `tests/test_audit_fixes.py::TestMamlAdaptationIsReal`
(3 tests) - confirms every parameter changes after adaptation, loss decreases
across the 3 inner steps, and `ClippedMAML`'s pre/post loss (the MAM-02
accept/reject gate) can now actually differ.

## Priority 2 — High

### 2A. SNN raw output had uncontrolled scale

**File:** `prometheus/neuro/spiking_network.py`

Added `InputScaleNorm`: rescales input to O(1) using the live batch's own mean
absolute value in train mode (an EMA-tracked running estimate is used in eval
mode, for batch=1 live inference). This directly targets the diagnosed mechanism:
`LIFNeuron`'s `v_thresh` is a fixed `1.0`, but real per-bar returns are
~1e-3-1e-2 - two to three orders of magnitude below it - so membrane voltage
almost never approached threshold for typical bars.

**Deviation from the suggested patch, and why:** did *not* add a `tanh` (or any
bounding activation) to the readout layer. Both real callers of this network
already apply their own external `tanh` to whatever it returns -
`prometheus/engine.py`'s `train_snn_step()` (`pred = torch.tanh(pred)`) and
`kronos/reflex.py`'s `ReflexArc.infer()` (`torch.tanh(pred * size_scale)`).
Adding a second `tanh` inside the network would make both of those literally
`tanh(tanh(x))` - the exact "double tanh" failure mode this audit's own SNN
review explicitly checked for and confirmed does **not** currently happen.
Reintroducing it here would have been a regression, not a fix.

**Verified:** normalized input lands within an order of magnitude of unit scale
(previously ~1e-3); batch=1 eval-mode inference (the live production shape) does
not crash, unlike `nn.BatchNorm1d` would; gradients still flow through the new
layer. Full test: `tests/test_audit_fixes.py::TestSNNInputScale` (3 tests). Note:
absolute spike-rate/sparsity tuning (`v_thresh`, `tau_mem`) is a separate
hyperparameter question, out of scope for this fix - what's fixed is that the
input is no longer 100-1000x below the threshold's scale by construction.

### 2B. Live REFLEX ticks never saw intraday price movement

**File:** `kronos/orchestrator.py`

`self.state.memory` (a frozen `DailyMemory`) is set once per day before market
open and never reassigned during the ~375-tick trading session, so
`reflex.infer()` was fed an identical window on every tick. Fixed via a new
`_recent_returns_with_intraday()` helper: holds out `memory`'s most recent
historical bar and replaces it with a live "return since today's open" row,
computed fresh each tick from `bar_prices` against `self._day_open_prices` (a new
small piece of orchestrator state, reset once per day in `run_digestion()`) -
without mutating the frozen `DailyMemory` at all. Falls back to the old
pure-historical window when `bar_prices` isn't supplied (tests/simulations that
call `run_reflex_tick()` without live ticks).

**Verified:** `tests/test_audit_fixes.py::TestReflexIntradayUpdates` (2 tests) -
confirms the window's last row changes as price moves tick to tick, and that the
no-live-data fallback still matches the exact old behavior.

### 2C. Black-swan pretraining corpus came from an untrained neural network

**Files:** `prometheus/engine.py`, `prometheus/generative/diffusion_simulator.py`

Went with **Option 2** (train it), not Option 1 (remove it): the diffusion
simulator's `train_step()` was already a fully functional DDPM training step,
just never called anywhere - fitting it before generation is a genuinely small
addition, not a redesign, and removing the whole pretraining stage would be a much
bigger behavioral change to a stage the rest of the pipeline (`scripts/train.py
--mode pretrain`) is built around.

Added `PrometheusEngine._pretrain_score_net()`, called once (guarded by the same
`if not self.scenario_library.scenarios` check that already gates one-time
generation) before `generate_doomsday_library()`. Best-effort: uses
`real_returns` if passed in, otherwise attempts a `MarketDataFetcher` fetch; if
neither is available (no network, no data), proceeds exactly as before - an
untrained score network - but now logs **CRITICAL**, matching this codebase's
existing fail-loud convention elsewhere, instead of staying silent.

Also fixed `validate_tail_coverage()`'s near-tautological gate:
`kurtosis > -1.0 OR coverage_pct >= min_tail_pct` → `kurtosis > 0.0 AND
coverage_pct >= min_tail_pct`. The old `OR` with a near-universal kurtosis floor
meant the check could pass a distribution with 0% tail coverage, as long as it
wasn't extremely thin-tailed (Gaussian's kurtosis is already 0, comfortably above
`-1.0`) - it could never actually catch what it was designed to catch.

**Verified:** standalone test confirms the training loop converges (loss
1.28→0.84 on synthetic fat-tailed data in 150 steps) and flips a fitted network's
`validate_tail_coverage()` from failing to passing; offline-mocked tests confirm
both the fetch-failure fallback (doesn't raise) and the explicit-`real_returns`
path (`tests/test_audit_fixes.py::TestDiffusionPretrainFallback`, 3 tests).

## Priority 3 — Medium

### 3B. Asymmetric loss over-rewarded overconfident magnitude

**File:** `prometheus/loss/asymmetric_loss.py`

The correct-direction "overestimate" calibration floor was a bare constant
(`1e-4`), disconnected from `alpha` (a *trainable* `nn.Parameter` via
`log_alpha`) - at `alpha`'s default of 0.5 that's a ~1:5000 gradient ratio
between overestimating and underestimating by the same magnitude, and the ratio
only gets more extreme if `alpha` is learned upward during training.

**Note on scope:** `tests/unit/test_loss_kelly.py` has two existing tests that
explicitly encode this asymmetry as an intentional design contract -
`test_correct_direction_overestimate_has_zero_loss` and
`test_calibration_gradient_much_smaller_than_underestimate_gradient` (which
asserts the ratio stays under 1%). The fix respects that contract rather than
overriding it: `OVERESTIMATE_PENALTY_FRAC = 0.01` scales the floor by `alpha`
itself (`calibration = 0.01 * alpha * mag_error`) instead of using a disconnected
absolute constant, landing the ratio at ~0.99% - just inside the existing tested
bound, versus the old ~0.02%. That's a real ~50x increase in the cost of
overconfident overestimation, without reversing the tested "underestimating a
real edge costs more than overestimating" design intent. **No existing tests
needed to change** - all 16 tests in `test_loss_kelly.py` still pass as-is.

**Verified:** direct gradient-ratio measurement (0.00990, vs. 0.0002 before);
`tests/test_audit_fixes.py::TestAsymmetricLossBalance`.

## What's NOT changed / known compatibility note

- Architecture changes to `SpikingMarketEncoder` (2A, new `input_norm` buffer) and
  the shrunk NEAT genome `input_dim` (1A) mean any **pre-existing on-disk
  checkpoint** (RunPod-trained SNN weights, saved NEAT-evolved master models) is
  now stale and will fail to load with a shape/key mismatch. This is *expected
  and correct* fail-loud behavior, not a new bug: `kronos/runpod_trigger.py`'s
  `load_runpod_checkpoint()` already treats any `load_state_dict` exception
  exactly like "no checkpoint found" (log, return `False`, change nothing) by
  design, so the live RunPod-adoption path degrades gracefully. `--resume`
  against a pre-fix `PrometheusEngine` checkpoint would raise (not silently
  corrupt) - regenerate checkpoints under this code before resuming.
- Priority 3A (`CausalTransformer`'s cosmetic DAG masking) and the
  `scripts/train.py` `run_evolution()`-validates-against-random-noise issue were
  flagged in the audit but are lower-priority/architectural, not surgical
  one-file fixes, and weren't in this pass's scope.
- No performance claim is made anywhere above beyond what each fix's own test
  verifies. Whether real predictive edge emerges is exactly what the validation
  plan below is for - none of these fixes can be judged "worked" from a unit
  test alone.
